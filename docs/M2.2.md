# M2.2 — Backbrief and ordering

## Public behavior

The `backbrief` MCP tool records `backbrief.submitted`: the agent's
restated `goal`, its `plan` (`files` it intends to touch and a `lines`
estimate), its `expected_decisions` (each `question`, `category`,
`paths`, `intended_default`) and `will_not_touch` paths. An expected
decision with a missing or unknown `category` is rejected with the full
valid list; schema validation deliberately does not require the field so
the rejection carries the list (C2.2.2).

Ordering (M2.2): a session registered with `require_backbrief` denies
every non-read-only tool call at `PreToolUse` with the reason
"Submit your backbrief first" until that agent's `backbrief.submitted`
is in the ledger. The read-only list is fixed in the adapter —
`Read`, `NotebookRead`, `Glob`, `Grep`, `LS` — plus
`mcp__court__backbrief` itself, the only way out of the gate. Read-only
calls before the backbrief are allowed and recorded (C2.2.3). The gate
also applies at the MCP boundary, so a call that bypassed its
`PreToolUse` hook still cannot write ahead of the backbrief.

Revisions (C2.2.4): a second `backbrief` from the same agent records a
second `backbrief.submitted` — the ledger is append-only, so the first
stands and the expected decisions of both are kept.

`await_clerk` (dormant here, used in M2.3) additionally holds the
agent's first write until the commission's clerk list is recorded.

## Check results

C2.2.1–C2.2.5 PASS (MM2.2: 0 violations in 500 scripted commissions).
Sabotages: `backbrief-not-required` and `write-tool-classed-read-only`
caught by C2.2.1; `revision-overwrites-first` — a natural-key dedupe
that would drop the second submission — caught by C2.2.4.
